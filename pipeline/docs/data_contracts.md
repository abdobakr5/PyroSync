# Data Contracts (Plan Step 2)

These are the agreements between Data Engineering and each consumer team. A breaking change (a renamed or removed column, a changed meaning or unit) needs a new version and a message to the team **before** it ships. Adding a new column is not a breaking change.

> Status: **proposed by Data Engineering.** Each team should confirm or ask for changes. The frontend is already building against contract 1.

## 1. Frontend: static JSON files (version 1)

Published in `data/gold/current/calendar/`. The files are regenerated by every Gold run.

### calendar.json
```json
{ "meta": { "daily_columns": ["date","harmonized","modis_fire_cells","viirs_fire_cells","frp_mw","source",
                              "percentile","level","frp_percentile","frp_level"],
            "levels": ["none","low","normal","elevated","high","extreme"],
            "start": "2003-01-01", "end": "2025-12-31", "unit": "...", "frp_unit": "..." },
  "regions": { "<Country>": { "daily": [[...], ...],
                              "climatology": { "p50": [365], "p90": [365], "frp_p50": [365], "frp_p90": [365] } } } }
```
- **One row per day**, with no gaps between `start` and `end`.
- **`harmonized`:** VIIRS-equivalent fire-cell-days (extent).
- **`frp_mw`:** VIIRS-equivalent heat (intensity).
- **`source`:** `"VIIRS"` or `"MODIS x ratio"`.
- **`percentile`:** null only when there is no history for that day.
- **Climatology arrays:** index 0 is day-of-year 1.
- **Combined level** (the worse of `level` and `frp_level`) is computed by the frontend, or comes from the database view `v_fire_calendar`.

### monthly_grid.json (map, month slider)
```json
{ "meta": { "columns": ["lat","lon","region","fire_days","frp_mw"], "region_names": [...], "months": ["2003-01", ...] },
  "data": { "2021-08": [[38.95, 23.25, 2, 6.0, 12273.2], ...] } }
```
- **`lat`/`lon`:** the cell centre. Draw the square as ± 0.05°.
- **`region`:** an index into `region_names`.
- **Every month** from the first to the last is a key. A month with no fire has an empty list.
- **Border cells** appear once per country. Add up rows with the same lat/lon to show all countries together.

### cells_summary.json (typical-year base layer)
Columns:
- `lat`, `lon`, `region`
- `fire_days_per_year`, `frp_mw_per_year`
- `peak_month` (1–12)
- `mean_fire_days_by_month` (12 values)

## 2. Backend: PostgreSQL / PostGIS (version 1)

- **Schema `firms`:** created by `sql/migrations/`, which are applied automatically by `publish`.
- **Tables:**
  - `detections`
  - `detection_comparisons`
  - `hotspot_statistics`
  - `regional_fire_trends`
  - `fire_calendar_daily`
  - `monthly_grid`
  - `calibration_ratios`
  - `calendar_validation`
  - `pipeline_runs`
- **Views:**
  - `v_fire_calendar` (adds `combined_level`)
  - `v_comparison_summary`
- **Geometry:** a `geom` column in SRID 4326, generated from lat/lon (points for detections, 0.1° squares for grid cells). It has a GiST index. For GeoJSON, use `ST_AsGeoJSON(geom)`.
- **Time:** `acquisition_timestamp` is `timestamptz` (UTC). Calendar dates are local solar dates.
- **Filters supported by indexes:**
  - date range
  - instrument + date
  - region + date
  - match status + date
  - bounding box (`geom && ST_MakeEnvelope(...)`)
  - distance from a point (`ST_DWithin`)
- **Pagination:** `ORDER BY <time>, <id> LIMIT/OFFSET`. Keep `LIMIT` ≤ 5,000 rows for detections. Use `monthly_grid` / `regional_fire_trends` for map overviews instead of raw detections.
- **Refresh:** each publish replaces Gold tables in one transaction and upserts detections. Readers never see half an update. The last successful publish is in `pipeline_runs` (example query 8).
- **Ownership:** Data Engineering writes; Backend has read-only access. Connection details are shared privately, never in Git.
- **Example queries:** `sql/example_queries.sql` (all tested).
- **Known nulls:**
  - `fire_type` for NRT rows
  - `distance_m` / `time_difference_seconds` for `*_only` rows
  - one of the two detection IDs in comparison rows
  - `modis_match_rate_pct` in months with no MODIS detections

## 3. AI Engineer (version 1, to confirm)

**Input:** `data/gold/ai/<gold_run_id>/model_input.parquet`
- **Grain:** one row per compared detection, keyed by `detection_id`. Every row traces back to Silver and Bronze.
- **Features:** listed with units in `model_input_schema.json`.
- **Missing values:** `other_sensor_distance_m` is null when the other sensor detected nothing in the time window. No values are imputed.
- **Splits:** temporal (`split`: train ≤ 2019, validation 2020–2021, test ≥ 2022), plus `spatial_block` (1° tile) for spatial cross-validation. This avoids leakage between nearby or simultaneous detections.
- **Questions for the AI Engineer:**
  - What is the task (e.g. predict whether the other sensor detects the fire, or flag unusual detections)?
  - Is this grain right, or should it be candidate pairs, grid cells or time windows?
  - Which features to add or remove?

**Output** (one row per prediction):

| Field | Type |
|---|---|
| prediction_id | string, unique |
| input_record_id | string, a `detection_id` from the model input |
| model_name, model_version | string, required |
| prediction_label | string |
| prediction_score | float; its meaning must be documented (not assumed to be a probability) |
| inference_timestamp | UTC timestamp |

Outputs are checked with `src.analytics.ai_dataset.validate_predictions()` before they are stored.
